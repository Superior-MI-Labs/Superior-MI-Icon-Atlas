# Declarative concept actions and production

Patch E/F contract slice of #53. This extends the same concept definition, ruleset registry and contributor resolver. It is deliberately not a gameplay executor, combat simulator, inventory implementation or crafting engine.

An optional actions map (up to 64) defines a kind, optional description, requirements and ordered operations. Host role names actor (initiator), subject (item/entity carrying the action), target (recipient) are symbolic until the host binds authoritative instances. The same subject concept may have several actions. A named action kind such as consume, attack, repair, equip, unlock, harvest or craft is descriptive, not an authorization or a new runtime opcode.

Requirements: inventory.has (concept item ref and positive integer quantity), state.is (axis and value), capability.has, stat.at_least (fixed magnitude). Operations: inventory.consume, inventory.produce, stat.consume (positive fixed magnitude), stat.change (increase/decrease, nonnegative quantity/dice/proportion), state.set (explicit enum state only for the subject), event.emit. Each operation can optionally have a boolean property guard. Item refs use a concept ID and optional exact archive digest. Costs, outputs, catalysts and reusable tools are represented through existing requirements and operations rather than a separate recipe language. A recipe is a craft action on its output or workstation concept. An item consumed in a recipe must have a consume operation; merely requiring a reusable tool never consumes it.

Magnitude is either a typed concept value or {"property":"health.restore"}, referencing the selected contributor resolver property. A guard such as {"property":"consume.return_container","equals":true} can make a returned bottle optional. Property references are resolved only when the host chooses modules and sources; an unresolved property is reported, never interpreted as zero. Fixed quantities are nonnegative; effect direction is explicit. Dice/proportion stay symbolic. Derived state axes cannot be directly changed on the subject; hosts must validate the actual state contract of other bound roles.

Call VisualAtlasCollections.planConceptAction(registry, concept, actionID, contributors, rulesets, selections, overrides). It returns conflict, missing, empty, or planned, with a copied immutable-data operation plan (no mutation of inputs). Planned is not authorized or committed. The host must bind participants, verify exact item identities/versions, permissions, actual inventory, resource limits, state, cooldown and target constraints; evaluate dice/proportions and modifiers under its chosen rules; reject or apply all requirements/costs/effects/outputs atomically under one host transaction ID; deduplicate replay and publish semantic events after success. Costs and outputs must be validated as a whole, including capacity and partial failures. No animation marker or imported event authorizes a game mutation. Do not execute actions on catalog download, render or preview.

The initial fixture uses a potion with optional empty bottle and a craft action that requires but does not consume a brewing tool. It demonstrates data and planning, not actual host inventory execution. Future runtime host qualification, material property and equipment slot registries, recipe quantities beyond discrete items, timed actions and spatial assemblies require separate implementation and tests. Existing stat-core preview runtime remains unchanged.
