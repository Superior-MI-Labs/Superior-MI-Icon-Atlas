# Concept graph and state projection

Patch C/D, issues #52 and #53. This optional extension reuses the pack's concepts, concept_id, render assets, collection resolver and export. It does not create another renderer or state store.

## Semantic edges
Concept capabilities are declared identifiers, not runtime support certificates. A relationship is a typed edge to a concept or existing visual asset ID, optionally pinned by archive_sha256. Types: represented_by, compatible_with, requires, produces, transforms_into, unlocks, repairs, equips_to, applies_effect, triggers, harvested_from, uses_animation, uses_effect, uses_audio, contains. No arbitrary executable operations. A relationship is a discoverable assertion, not permission, dependency, recipe execution or containment geometry. Self and reciprocal semantic relationships may be valid; actual render dependencies remain in the existing acyclic dependency graph. No semantic edge is automatically loaded or included in selected export. The selected ZIP preserves edges even if the targets are absent; conceptGraph reports local availability only for unpinned references resolved in the supplied archive. Pinned references require host-side verification. Reverse links are derived, not authored twice. A contains edge is descriptive; recursive physical assembly rules will be separate from semantic containment.
 
## State axes and representation
A concept may define independent enum axes (values, optional default) and ratio axes (current and maximum host stat keys, increasing inclusive upper-bound bands ending at 1). Example durability: maximum 100, bands 0 broken, .25 damaged, .75 worn, 1 intact. Missing current or max means unknown, not zero; invalid current or maximum rejects. Derived axes cannot be directly overwritten; enum axes may be selected by the host. All projection is pure, no live state stored by Atlas.

A visual asset can optionally declare representation.role and representation.when (state-axis/value selectors), in addition to its existing concept_id, style, perspective and medium classification. The concept must be present within that archive, selector values must exist. Roles are host-selected identifiers, e.g. inventory, world, portrait, attack. No new 3D kind or conversion from sprite to model. selectRepresentation chooses known selector matches, maximum specificity, and reports ambiguous ties. Conditional matches are allowed to leave orthogonal axes unspecified; unconditional art is a fallback only if explicitly allowed when state axes exist. If no axes exist, unconditional art is a match. Unknown states never satisfy a conditional selector. No invented angles or variants. Existing state_set, slots, sequences and compositions can be referenced as selected visual assets. Gameplay damage is never triggered by this selection.

The derived public catalog includes concept summaries (owner pack, identity, capabilities, ruleset and axis IDs, semantic relationships), plus optional per-asset representation metadata. The existing pack entry provides its archive locator/digest. Full definitions remain in the ZIP. No new public catalog or database. Duplicate authored public concept ownership fails the build. Old unresolved concept_id hints remain valid. No network fetching, cross-archive resolution or host migration is implemented by the pure graph helper; runtime host must use the exact pinned provider archive and qualify actual representation support. Export preserves associated concept records and notices without fetching all semantic neighbors.

Future steps: actual multi-pack pinned graph resolution, state event/animation marker protocol, host-authorized transactions, inventory/recipe/material and spatial assembly payloads. No gameplay or 3D support claimed.

Public search and private Builder search include declared concept names, functions and ruleset IDs while keeping visual capability facets separate. Public detail displays linked concept metadata and unpinned current-catalog associations. Pinned references are not silently redirected to a different current version. Existing public detail/related-assets controls are reused; no new navigation or state store.

### Exact runtime references

The shared ZIP core now resolves one concept/asset reference to a current catalog owner or an explicitly pinned digest route, then fetches a bounded same-origin response, verifies SHA-256 and checks requested ID membership after normal ZIP validation. Public browser and Builder use the same verified fetch helper; existing filename deep links remain unchanged. Old catalogs without immutable locators use the existing alias plus digest, never silently substitute on mismatch. A historical locator is only a request until actual verification; no guarantee of retained bytes. No persistent cache or automatic semantic-neighbor loading; host session cache remains responsible for deduplication. Actual Hex World adoption requires its own qualified vendor/adapter update.
