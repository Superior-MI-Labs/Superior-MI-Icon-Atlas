# World and environment artwork

Use this recipe for terrain, vegetation, natural props, architecture, furniture, interactive containers, directional artwork, water and environmental effects. Read the [format contract](../FORMAT-API.md) and [release checklist](../RELEASE-CHECKLIST.md). Load the [collections recipe](../collections/README.md) or [animation recipe](../animations/README.md) only when needed.

## Organization and public reuse

World assets are general-purpose Atlas assets, not a Hex World-exclusive library. Group by coherent visual style and asset family in independently maintained collections, for example `examples/painterly-fantasy-terrain`, `examples/painterly-fantasy-woodland`, `examples/painterly-fantasy-interactives`. Use one collection index and one or more canonical manifests. Group sheets by ownership and logical family; keep stable globally unique IDs independent of sheet arrangement and host application. Prefer new general-purpose IDs such as `smi.world.fantasy.woodland.fern.01`; do not rename published IDs. The canonical source is the actual asset manifest, not a separate catalog. Use existing domain, style, subject, tags and descriptions to support public discovery. Suggested domain: world-environment; subjects identify the family. Only describe actual authored features. Use the canonical optional spatial profile below; do not invent schema keys. Use the existing approved-publication gate and archive build; do not modify generated search indexes or register unapproved art in publications.json.

## Artwork and projection

Use measured transparent sheet regions for discrete objects, and seamless unprojected square regions for repeatable ground/cliff textures. Keep terrain, cast shadows and scenery separate from upright sprites. Preserve logical canvas, trim offset and normalized anchor through all views, states and frames. State the intended projection, elevation and camera-relative view convention in the pack README. Establish a canonical front before generating any directional sheets. Choose billboard/symmetric, four-, six-, eight-direction or custom view coverage based on the actual consumer. Do not imply camera-independent artwork for asymmetric objects. Mirroring is acceptable only if explicitly qualified for the particular art; do not mirror text, hardware, asymmetric lighting or handedness blindly.

Hex World currently uses six 60-degree yaw increments at 35.264-degree orthographic elevation. For its specific six-view contract, view 0 shows the front, view 1–5 follow successive positive camera yaw steps from front. Label views by indices and explicit angles, not ambiguous compass names. The host computes camera yaw relative to object orientation; changing camera does not mutate the object. Other hosts may use different conventions. Declare supported equally spaced views in the spatial profile below; document projection and any unsupported custom-angle pilot in the README. For view-dependent animation, qualify every view and state with matched pivots. If a complete directional set is not ready, declare a billboard fallback or incomplete pilot, not false coverage.

## Interactive and composable artwork

Use region, sequence, composition and state_set, not a new asset kind. Independent choices should remain independent. A chest can have a rear/interior, compatible contents slot (empty/gold/gems/potions), foreground wall, lid states (closed/opening/open/closing), and optional effect layer. Author occlusion in the layer order, hide contents appropriately when closed, and qualify each supported combination. Prefer a shared composition with typed enum/boolean inputs and state_from_input or visible_when over duplicating entire sheets for every combination. Direction-dependent layering may need separate matched compositions per view. Use versioned slot interfaces and explicit approved options, not similarity by tag; the current contract does not automatically accept arbitrary future packs. Presets are useful for convenient defaults; actual inventory, locked status, collision, damage, and game rules remain host-owned.

## Environmental capabilities

Use canonical states, sequences, layers and typed inputs for authored visual responses. A host may drive wind, contact, climate, time, activation or new application-specific inputs, but only via an explicit supported adapter. Preserve neutral defaults for unsupported inputs. Do not put scripts, simulation rules, arbitrary shaders or invented capability fields in a pack. Record the input names, units, allowed range, default, visual effect and demonstrated host support in README. Distinguish an authored visual affordance from verified runtime integration. Static flexible foliage can be deformed by a host; an animated wind sequence may also be used. Keep root/attachment pivots consistent. Effects should be reusable without a baked actor.

## Qualification and handoff

Begin with a small creator-approved pilot before bulk production. Inspect actual source fidelity and all measured crops, logical anchors, alpha, view changes, transitions, independent input choices, slots and presets. Verify the final ZIP through the existing builder and creator-specific acceptance runner. Use the audited exact-archive command with `--visual-spec` and the [rendered-state QA guide](../VISUAL-RENDER-QA.md); report browser samples and archive SHA-256 separately from artistic approval. Test unchanged parts as well as expected changes: camera changes must not alter the logical contents, and closed-container loot choices must not expose hidden pixels. For directional assets, test front/back and every declared view, with open/closed or relevant animation states. For reusable contents, verify empty/full choices, lid occlusion and alignment. For seamless terrain, inspect a repeated 3×3 preview. Report PASS/WARN/NOT RUN truthfully, including unsupported host features. Deliver self-contained ZIP, canonical IDs, measured texture paths, contact sheet, README, rights and QA receipts. No placeholder art presented as approved production assets.

For Hex World-specific size, material and environmental binding instructions see [production handoff](https://github.com/Superior-MI-Labs/Superior-MI-Hex-World/blob/main/docs/ART_PRODUCTION.md) and [environment artwork](https://github.com/Superior-MI-Labs/Superior-MI-Hex-World/blob/main/docs/ENVIRONMENT_ART.md). The host terrain/placement bindings remain separate; the canonical spatial profile supplies reusable visual height, views and wind. Hex World implements a six-view host binding (see [directional artwork contract](https://github.com/Superior-MI-Labs/Superior-MI-Hex-World/blob/main/docs/DIRECTIONAL_ART.md)); fixed-canvas root composition and compatible slot support are implemented, but qualify each actual asset against the host before claiming compatibility.

## Public runtime distribution
Use the existing public catalog (`public-catalog.json`) to resolve an asset's pack and its approved ZIP URL. The collection's `archive_sha256` identifies the exact published bytes; record it with any pinned release integration. The shared `zip-core.js` reader resolves the same canonical manifests and textures for the Builder, public preview and downstream hosts. No second manually published texture library. A release pending artistic review remains labeled pending; archive availability does not imply compatibility with every host. Do not republish an unpublished source or bypass the collection approval gate.

## Discoverable affordances and host events
The generated public catalog exposes `capabilities`, implemented `interfaces`, and accepted `slot_interfaces` derived from the canonical archive. The browser can filter by these. Animation is discovered through reachable sequences and timed compositions; root inputs, presets, slots and event handlers remain independent. These are descriptions of authored functionality, not a physics or host-compatibility certificate. For explicit world-object use, a root composition may declare the existing `behavior.on.use` event with typed `toggle`, `set`, or `emit` actions. A host can dispatch it only after its own reach/authorization checks. An `emit` is a notification, not a permission to mutate inventory, execute scripts, or change geometry. Use stable event/input names and matching contracts across directional views; unknown events fall back to no action. No implicit wind, fire, collision, or interaction support is derived from tags. Hex World consumes the shared renderer/interaction resolver and checks actual assets before committing visual state.

## Optional self-describing spatial profile
The asset-level `spatial` extension is now part of the canonical pack schema. Use it for actual authored world affordances, not gameplay. `height_ft` is a suggested visual height (0.1–100). `views` specifies `elevation_deg` and an ordered `assets` array of 4, 6 or 8 IDs, equally spaced in positive camera yaw relative to the object's front; index 0 must be the root asset ID. Secondary views must share the same root kind, state names/default, typed inputs, slot options, presets and behavior; do not give them their own directional profile. All view dependencies travel with a selected asset export. `wind` optionally specifies `bend` (0–1), `reference_speed_ft_s` (default 20), and increasing `states` thresholds with `min_speed_ft_s` and `state`. State thresholds require every view to expose those state names. These are optional presentation capabilities; actual wind and physical interactions remain host-owned. Hex World supports the six-view 35.264-degree profile and can use a neutral front fallback for unsupported angles. Unchanged older manifests remain valid. Verify through exact-ZIP QA including all views, states, roots and allowed combinations; the schema does not certify artwork quality.
