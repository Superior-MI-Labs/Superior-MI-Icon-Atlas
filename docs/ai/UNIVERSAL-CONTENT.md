# Universal asset and ruleset architecture

Status: first contract candidate, 2026-11-27. This document is the cross-project design baseline, not a claim of complete gameplay integration.

## Principles
- Atlas is the content authority: artwork, concept definitions, portable suggested mechanics, relationships and spatial payloads. Hex World owns terrain, placement, physics, collision and world instances. Tabletop or other host owns gameplay authority, inventory, time, random draws, transactions and saves.
- Separate stable visual asset IDs, concept IDs, versioned ruleset IDs and host instance IDs. Legacy art and unresolved concept_id discovery hints remain valid. No bulk renaming or forced gameplay metadata.
- Original authoring and familiar numerical defaults are CC0 when rights permit; attribution appreciated, not required. Preserve separate third-party licenses/notices. No proprietary rules compendium or official compatibility claim.
- Data is not code. Do not execute scripts from content. Unsupported capabilities must be diagnosed; missing is unknown, not zero. Definition values are editable defaults, not requirements imposed on a host.
- Visual representation (pixel size, pivot, crop, spatial.height_ft visual hint) and physical dimensions (real-world scale) are distinct. Do not derive physical collision automatically from pixels.

## First milestone: canonical concept records
Optional pack-level concepts use smi-concept/1. An existing visual asset's concept_id links to a definition; several visuals may share it. A declared definition must be linked to at least one visual in the same ZIP; duplicate declarations inside one ZIP reject. Identical definitions can coexist in separate imported bags, conflicting definitions reject. Unresolved legacy concept IDs remain hints, not errors. No requirement to enrich old assets yet.

Physical properties use SI: width_m (local lateral), depth_m (local forward), height_m (vertical), mass_kg, capacity_l. All positive when present; omit unknown. These are suggested concept properties, not authoritative collision or rendered sprite scale. No automatic conversion to the existing visual height hint.

Defaults is a map keyed by versioned rule module IDs such as smi.rules.d20/1. Each profile maps namespaced stat keys to one of quantity (finite value and unit), dice (count, sides, integer modifier and unit), boolean. These are bounded typed data, not executable formulas. Units are identifiers (e.g. hp, s, count); the shared stat registry and conversion rules are future work. No implicit conversions. The test fixture tests 2d4+2 HP, 5 HP, a bonus action cost, use duration/cooldown and optional empty-container policy. Values are illustrative independently authored defaults, not a specific tabletop rules license.

The shared collection resolver preserves declared concepts across multiple manifests, and selected public/private exports preserve only definitions linked to chosen visuals, together with concept license notices. Imports keep bag ownership. The pure resolveDefaults helper selects explicit modules; overlapping unequal keys reject instead of stacking, unknown modules reject. Explicit application overrides of selected keys preserve units and boolean/numeric category; a dice magnitude may be replaced by a flat quantity of the same unit. Output is copied, not a mutation of source. No random rolls or consumption occur in this helper. This is not a full rule-module registry or runtime transaction engine.

## Next phases and acceptance gates
1. **Live provider and retention:** keep public-catalog.json derived from approved manifests. Add concept summaries and locators once cross-archive ownership/retention is defined; resolve versioned dependencies lazily by exact digest and cache. Static Pages can serve the first provider; immutable release retention issue #47 is a prerequisite to durable saves. Export and runtime must share resolution semantics. Old saves must recover pinned bytes or report missing data.
2. **Typed registry:** define unit/type/aggregation/range semantics, versioned independently composable dice, d20, flat, proportion, turn, action economy, AP and real-time modules. Validate profile conflicts and supported operations. No implicit active ruleset or mixing conflicting healing interpretations. Host overrides before instance modifiers; original definitions stay immutable. Existing stat-core and stat_profiles retain their preview runtime role; reuse/extend only when semantics match.
3. **Functional graph:** explicit typed relationships for visual roles, recipes, inputs/outputs, locks/keys, traps, harvesting, equipment and effects. Model transformations as host transactions; returning an empty bottle is an optional rule/policy. Recipe inputs distinct from reusable tools, catalysts and byproducts. Reverse links derived, not independently maintained. Render dependency DAG is separate from semantic relationships that may legitimately form cycles (bottle -> potion -> bottle). Only dependency edges traverse export/load closure; no unbounded graph chasing. Add actions only with all-or-nothing validation, target rules, costs, timing, typed effects and host permissions; never let animation markers authorize damage.
4. **Spatial assembly:** physical bounds are not a footprint. Define local anchor/frame, occupied volume, required empty/excavation volume, clearance, support, entrances/connectors, floor/room/environment regions, nested components and payload grid representation. Independent floor footprints, negative elevations, and sparse irregular geometry are supported goals. Reuse Hex World's smi-hex-prefab/1 and validated World.apply/edit-plan history, not a second terrain model. Atlas distributes versioned host-specific spatial payloads; Hex World rotates and translates coordinates, checks unknown geometry, clearance, support, collisions, affected entities and materials, previews excavation/foundation edits and commits one atomic reviewed plan. Never automatically carve terrain on load. Continuous same-world caves and buildings, not portals unless intentionally authored. Other grid payloads require explicit adapters; no automatic exact conversion. Reject recursive assembly dependencies.
5. **Animation/effect relationships:** preserve canonical regions, sequences, state sets, compositions and spatial.views. Add typed presentation markers, attachments and linked effects/audio only once an event contract is defined. Host owns movement and effect authority; six-view accuracy requires qualified physical camera convention.
6. **Editing/discovery/AI:** extend existing catalog/Builder/inspector rather than a second database. Capability search must distinguish declared, structurally valid, supported, host-qualified and artist-reviewed. AI and manual requests resolve the same pinned data and validated plans. No speculative migration of entire catalog until pilots pass.

## Qualification pilots
- Potion + empty bottle: same concept across icon/world representation; d20/flat alternatives; AP/real-time; return/discard policy; recipe and resource transaction. Reject duplicate or partially applied consumption.
- Sword: dimensions, equipment slots, wear, repair, sheathed/drawn visual states; no duplicate item instances when appearance changes.
- Chest/key/trap: lock interface, detection/disarm, opening visual, contained items, optional trap event; reject unauthorized interactions.
- Fireball: icon, cast/release/impact visuals, linked effect, selected ruleset damage; no damage triggered from rendering.
- Tree/rabbit: scale, harvesting or mobility, view/state transitions, environmental response.
- Tavern/cave: unequal floor bounds and negative levels, narrow entrance, explicit voids, rotation, conflicting terrain, undo and exact save/reload. Use actual Atlas content in Hex World, not a mock second renderer.

## Delivery order
First contract and import/export tests; then provider retention and registry; then transaction/relationship slice; then spatial pilot and host qualification. Keep full repository CI and existing asset QA. Each milestone gets one cohesive tested candidate; do not bulk-add speculative metadata. The first milestone does NOT implement gameplay, a public concept index, recipe execution, geometry ingestion, or automatic Hex World bindings.

## Patch A: immutable archive provider
Current catalog retains legacy demo/<slug>.zip compatibility aliases and projects immutable_zip from archive_sha256, as archives/sha256/<digest>.zip. The exact generated bytes are copied, never re-encoded. Discovery requires no ZIP download. The main-only retention job runs after the full build/browser gate, appends qualified archives to the dedicated atlas-archive-retention Git branch (no force push), and materializes retained bytes into Pages. First bootstrap imports only the immediately preceding live approved catalog's verified ZIPs; pre-bootstrap historical pins cannot be guaranteed. A missing branch after immutable publication, hash mismatch, oversized blob or site budget exhaustion blocks release; never evict retained saves. Historical archives are retained content, not searchable current publication entries. Current aliases remain for existing browsers/hosts; Hex World should prefer immutable_zip when available and explicitly recover legacy pinned aliases via the known provider's digest locator after qualification. No new server, no new catalog, no texture streaming within ZIP. Git storage and Pages size are finite; storage migration will be required before the budget gate. PR tests use an isolated fake prior catalog and two successive releases; actual branch bootstrap and live cross-origin host checks require main deployment. See #47 and #53.

## Capability discovery offers

Optional `concept.discovery_offers` is a bounded map of offer IDs to a role and a conjunction of requirements. An independently authored enhancement, tool, effect or resource describes what it needs; older targets need not enumerate it. An offer is a discovery assertion, not an action, attachment instruction, dependency or proof of host support. Preserve the existing semantic graph and exact runtime resolver. The initial operators are `capability.has`, `interface.has` (existing representation interface names), `fact.equals` (boolean, enum, quantity), `quantity.range` (inclusive same-unit bounds). Scopes are concept, representation, context. Empty requirements and executable expressions are rejected. No implicit class inheritance or chaining; missing facts stay unknown. A known contradiction dominates missing information. A scope without requirements is not a positive support certificate.

The existing catalog projects optional authored concept physical values and offers alongside capabilities, relationships and representations. The shared collection core `createDiscoveryIndex(catalog,{catalog_sha256})` derives one in-memory index from a validated current catalog. It accepts explicit exact subject/offer locators and optional typed query context, returns distinct compatible/unknown/incompatible groups with totals, bounded results and requirement-level evidence. `catalog_sha256` is caller-supplied snapshot identity, not verification by this pure function; the existing exact provider remains authoritative for archive retrieval. Known concept capabilities and same-owner concept definitions plus existing asset interfaces provide positive evidence. Unresolved cross-pack concept hints and absent declarations are unknown. Legacy/hidden/unpinned assets remain browseable by existing mechanisms but are excluded from exact compatibility lookup. Host context is labeled as such. No permissions, art-review status, actual render compatibility certification or consumer qualification are inferred. `rankEligible` for reverse asset queries applies existing `rankRelated` to all eligible candidates, with explicit semantic/color/style weights, evidence dimensions and unranked retention; similarity is not a mandatory filter or probability. Use the same query in either direction, never store every calculated relationship in each manifest.

First qualification pilots: add dark/light offers to a new catalog snapshot and show both directions discover them on unchanged sword definitions; independent mechanical/render scopes, unknown legacy metadata, explicit contradictions, exact locator mismatch, units and false/zero handling, deterministic bounded results; then seasonal fern/overlay and numeric HUD resources with the same matching contract. Existing pinned instances and dependency closure remain unchanged. Actual published offers, exact provider verification, real-browser Inspector, host acceptance, more complete context/physical predicates, indexing benchmarks and wider metadata enrichment require subsequent qualification. No existing asset migration or new global registry.

### Public Inspector presentation

The existing asset-detail relationship panel consumes `createDiscoveryIndex` directly. Its index is built once from the same public catalog response; SHA-256 is computed from the exact response bytes to identify that snapshot, not to establish authenticity. Catalogs without offers do not build a discovery index. Unsupported crypto or invalid optional discovery projections disable only discovery. Forward results group matched declarations, incomplete evidence and contradictions; reverse queries run when the user expands an authored offer. Each result shows separate concept, representation and context statuses plus requirement evidence. Navigation checks the exact archive digest against the current catalog and uses an existing visible same-owner representation; it does not invent an image or retrieve a ZIP until the user chooses the existing detail action. Each group displays at most eight results with the full count. No context or host qualification is guessed. No offer is activated by browsing. Private Builder imports need a separately qualified identity/provenance adapter to the same discovery contract; do not silently associate an imported or historical asset with the latest public concept.
